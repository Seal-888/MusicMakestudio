# PLI Music Studio

AI 음악 채널을 운영하는 데 필요한 작업을 한곳에 모은 작업실입니다.
채널 기획 → 가사와 Suno 스타일 만들기 → 마스터링 → 메타데이터 · 자막 → 채널 · 수익 분석까지 이어집니다.

내 맥에서만 도는 버전입니다. 서버도 로그인도 없고, 브라우저가 Gemini · YouTube API를 직접 부릅니다.
마스터링은 API 없이 이 브라우저 안에서 계산합니다.

## 시작하기

1. 이 폴더를 원하는 곳에 둡니다.
2. `run.command`를 더블클릭하세요. 터미널이 열리고 브라우저가 뜹니다.
3. 처음이라면 **API 설정**에서 키를 넣고 **테스트**를 눌러 초록불을 확인하세요.
4. 왼쪽 위 버전(예: `v84 · 10-25`)이 최신 커밋과 맞는지 보면, 새 파일이 반영됐는지 알 수 있습니다.

`run.command`가 안 열리면 터미널에서 한 번만:

```bash
cd <이 폴더 경로>
chmod +x run.command
xattr -d com.apple.quarantine run.command
```

두 번째 줄이 꼭 필요합니다. 인터넷이나 압축 파일에서 받은 파일에는 macOS가
격리(quarantine) 표시를 붙이는데, 실행 권한만 줘서는 이게 안 풀립니다.
`xattr`가 "그런 속성 없음" 오류를 내면 이미 풀린 것이니 넘어가면 됩니다.

이래도 "확인되지 않은 개발자" 경고가 뜨면 파일 우클릭 → **열기**를 고르세요.

### 왜 파일을 그냥 열면 안 되나요

`file://`로 열면 ES 모듈과 마스터링 계산(Web Worker)을 불러오지 못합니다. 꼭 `run.command`로 여세요.
`run.command`는 `serve.py`로 `localhost:8383`에만 서버를 띄웁니다. 같은 포트를 다른 폴더(예전 버전)가 쓰고 있으면 알려 줍니다.

### 브라우저

**Chrome 또는 Edge**를 권합니다. 마스터링은 모듈 Web Worker를 쓰므로 Safari는 15 이상이 필요합니다.

## 마스터링은 어떻게 동작하나요

파일은 어디로도 보내지 않습니다. 계산은 `js/mastering/worker.js`가 백그라운드에서 돌려, 긴 곡에서도 화면이 멈추지 않습니다.

1. **분석** — 음량(ITU-R BS.1770 LUFS), 트루피크(4배 오버샘플), 대역 밸런스 6구간, 저중역 탁함, 좌우 상관도 · 스테레오 폭을 잽니다.
2. **판단** — 기준에서 벗어난 것만 골라 처리 계획을 세웁니다. 대역 기준의 허용 폭이 넓어서, 밸런스가 괜찮은 곡은 EQ가 거의 걸리지 않습니다.
3. **처리** — 필요한 EQ, 저역 스테레오 조이기 · 중역 넓히기(좁은 믹스일수록 많이), 고역 제어, 글루 컴프레션을 겁니다.
   AI 생성곡(체크하거나 파일 정보에 Suno · Udio 등이 있으면)은 고역의 금속성 잡음을 따로 누릅니다.
4. **마감** — 목표 **−9 LUFS**, 천장 **−0.5 dBTP**로 리미터를 걸고 음량을 맞춥니다. 이미 큰 곡은 더 키우지 않습니다.

결과 화면에서 원본 · 마스터를 즉시 바꿔 듣고(A 키), 음량을 맞춰 소리 차이만 비교할 수 있습니다.
톤 · 저역 · 다이내믹 · 음량을 조절해 다시 마스터링하고, WAV 24/16-bit(48 kHz, TPDF 디더)로 내려받습니다.
**믹스 체크** 탭은 처리 없이 측정만 해서 발매 전에 고칠 것을 알려 줍니다.

기준값과 처리량은 다른 마스터링 서비스의 공개 데모와 실제 곡 몇 쌍(원본 · 결과)을 같은 원본에 이 엔진을 돌려 비교하며 맞췄습니다.
근거가 다섯 곡이라, 곡을 더 비교할 때마다 `js/mastering/engine.js`의 `decide` 숫자를 다시 맞추는 것이 정상입니다.

## 키는 어디에 저장되나요

이 브라우저의 localStorage에만 저장됩니다. 어디로도 전송되지 않고, 이 폴더 안에도 기록되지 않습니다.
대신 **브라우저 데이터를 지우면 같이 사라집니다.** API 설정 맨 아래 "파일로 내보내기"로 가끔 백업해 두세요.

**백업 파일에는 API 키가 그대로 들어 있습니다.** 이 저장소는 공개이므로 백업 파일은 앱 폴더 밖(다운로드 폴더 등)에 두세요.
실수로 넣어도 올라가지 않게 두 겹으로 막아 두었습니다.

- `.gitignore` — `plimusic-backup*.json` 같은 백업 파일 이름은 `git add` 에서 빠집니다.
- `.githooks/pre-commit` — 이름을 바꿨거나 `git add -f` 로 넣어도, 커밋할 내용에 API 키(`AIza…`)가 보이면 커밋을 멈춥니다.
  `npm install` 을 한 번 하면 자동으로 켜집니다. (`npm install` 없이 켜려면 `git config core.hooksPath .githooks`)

## 디자인 규칙

오래 켜 두고 작업하는 음악 작업실이라 **다크 스튜디오** 한 가지 테마만 씁니다. 색은 전부 `css/style.css` 맨 위 `:root`에서 정합니다.

| 역할 | 변수 | 값 |
|---|---|---|
| 페이지 · 카드 · 입력/박스 바탕 | `--bg` · `--card` · `--base` | `#0F141A` · `#161D26` · `#1D2632` |
| 선 · 테두리 | `--line` · `--border` | `#263140` · `#334050` |
| 제목 · 본문 · 보조 글자 | `--heading` · `--ink` · `--ink-soft` | `#F3F6F9` · `#E4EAF0` · `#9AA8B6` |
| 강조색 (하나뿐) | `--primary` | `#8FA3FF` |
| 상태: 성공 · 주의 · 오류 | `--green` · `--gold` · `--danger` | `#5CC08A` · `#E0B054` · `#EF7A66` |

- **강조색은 주요 동작과 현재 선택에만** 씁니다. 보조 버튼은 테두리만(`.btn.is-ghost`), 삭제는 코랄 테두리(`.btn.is-danger`).
  버튼을 색깔별로 칠하지 않습니다. 예전 이름 `is-blue` · `is-green`은 주요 동작과 같은 모양으로 그려집니다.
- 글자 대비는 본문 14:1, 보조 7:1, 입력칸 안내 5.3:1 이상을 지킵니다. 11px보다 작은 글자는 쓰지 않습니다.
- 카드 안에 또 상자를 두지 않습니다. 묶음은 간격과 가는 선으로 나눕니다.
- 아이콘은 이모지 대신 `js/render.js`의 `icon()` 선 아이콘을 씁니다. 같은 굵기로 그려져 화면마다 모양이 같습니다.
- 마스터링 화면은 `.mst` 아래에만 스타일을 두고, 그래프(canvas)도 같은 CSS 변수를 읽어 그립니다.

화면을 고친 뒤에는 [Impeccable](https://github.com/pbakaus/impeccable) 탐지기로 한 번 훑어보면 좋습니다.
앱을 띄운 채로 `npx impeccable detect http://localhost:8383/#/music` 처럼 화면마다 돌립니다. 지금은 9개 화면 모두 0건입니다.

## 고치기 전에 검사부터

의존성을 한 번만 받아 두면 됩니다.

```bash
cd <이 폴더 경로>
npm install
npm test
```

13종이 모두 통과하면 안전한 상태입니다. 브라우저 없이 돕니다. 코드를 고친 뒤에는 항상 한 번 돌려 보세요.

| 검사 | 확인하는 것 |
|---|---|
| `check-imports` | import 하는 이름이 실제로 export 돼 있는지, 메뉴와 라우터의 화면 목록이 맞는지 |
| `check-functions` | 부르는 함수가 정의돼 있는지, 알약 버튼이 눌리게 연결됐는지 |
| `smoke-test` | 모든 화면이 실제로 그려지는지 |
| `check-flow` | 가사 만들기 버튼을 눌러 결과 화면까지 가는지 |
| `check-draft` | 자동 저장 → 화면 재진입 → 이어서 하기 |
| `check-reference` | 레퍼런스를 고르면 옵션이 맞춰지고, '쓰지 않기'로 되돌아오는지 |
| `check-storage` | 저장소가 조용히 데이터를 잃지 않는지 |
| `check-seeds` | 2단계 생성(후보 → 고르기 → 완성)이 도는지 |
| `check-hook` | 후렴 훅이 제대로 반복되는지 |
| `check-subtitle` | 자막 글자를 바꿔도 시각이 그대로인지 |
| `check-review` | 유튜브 데이터를 쓰는 화면들과, 검토에서 고친 것이 되돌아가지 않는지 |
| `check-mastering` | 사인파로 음량 · 트루피크 측정을 확인하고, 마스터가 천장을 넘지 않는지, WAV 형식이 맞는지 |

`npm test`는 맨 먼저 `bump.mjs`를 돌려 `js/version.js`의 버전을 갱신합니다.

## 폴더 구조

```
index.html          화면 뼈대와 사이드바
css/style.css       전체 스타일 (맨 위 :root 가 색 · 글꼴 팔레트, 아래쪽 .mst 가 마스터링 화면)
js/app.js           페이지 전환 (라우터)
js/store.js         localStorage (키, 보관함, 저장 공간)
js/ui.js            알림 · 화면 벗어날 때 확인 같은 공용 조각
js/render.js        결과 화면 공용 조각, 선 아이콘(icon)
js/api/             Gemini · YouTube 호출
js/videostats.js    유튜브 영상 통계 (하루 평균 조회수 · 쇼츠 구분) — 분석 화면들이 같이 씀
js/audio.js         곡 길이 재기
js/lyrics.js        가사 규칙 검사 · 자막 줄 맞추기
js/prompts.js       Gemini 프롬프트 ← 결과가 마음에 안 들면 여기를 고치세요
js/version.js       bump.mjs가 만드는 버전 표시 (직접 고치지 않음)
js/pages/           화면별 코드 (메뉴 하나에 파일 하나)
js/mastering/       마스터링 엔진
  engine.js           분석 · 판단 · 처리 · 마감 계산 전부 (화면과 무관, 검사에서도 바로 불러 씀)
  worker.js           engine.js 를 백그라운드에서 돌리는 Web Worker
  wav.js              WAV 24/16-bit 내보내기
docs/               캡컷 draft 포맷 해독 문서 (기능은 제거됨, 참고용)
serve.py            로컬 정적 서버 (localhost 요청만 받음)
run.command         더블클릭 실행 (서버 + 브라우저)
bump.mjs            git 커밋 수로 버전 갱신
check-*.mjs         브라우저 없이 도는 검사들 (npm test)
smoke-test.mjs      모든 화면 그려 보기 검사
```

바꿀 일이 가장 많은 곳은 `js/prompts.js`입니다. 가사 · 스타일 결과물 품질은 거의 다 거기서 결정됩니다.
마스터링 결과가 마음에 안 들면 `js/mastering/engine.js`의 `decide`(무엇을 얼마나 걸지)를 고치세요.
